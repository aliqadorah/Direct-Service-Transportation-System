# Security review — account changes (owner testing 21 Oct 2026, item 2, DT-229)

Scope: name / username changes by the Owner or an Administrator in Users & roles (`PUT /companies/{company}/users/{user}`); email change by the user (`POST/DELETE /me/email`), started by an Owner / Administrator (`POST/DELETE /companies/{company}/users/{user}/email`), confirmed by the account's user (`POST /auth/confirm-email-change`, page `/confirm-email-change`); `EmailChangeService`, `UserAdminService.UpdateUserAsync`, `AuthService.VerifyReauthenticationAsync`, the new email templates, `core.Users.PendingEmail` / `PendingEmailAt`, the profile and Users & roles screens. Method: an independent read-only review of the change against the existing identity code (AuthService, AccountService, GrantGuard, SessionService, AuthEndpoints, AccountPage, Program.cs), then fixes and regression tests.

## Findings and what was done

| # | Severity | Finding | Status |
|---|---|---|---|
| F1 | Medium | Adding a username to a user who signs in with their email would make the administrator's "set password" available for that user (the rule is "has a username") — an Administrator could then set a password and sign in as them. | **Fixed:** a username is changed, never added to an email user (`user.userNameNotForEmailUser`); the dialog shows the username field only for users who have one. Test: Owner's own row refused. |
| F2 | Medium | Clearing a username of a user with an unverified, administrator-entered email would make that email count as self-registered, so whoever holds the (possibly mistyped) mailbox could verify it without signing in and reset the password. | **Fixed:** a username cannot be cleared (`validation.required`). Test. |
| F3 | Medium | Confirming did not change the security stamp: links already sent (e.g. a password reset to the old address) stayed valid up to 24 h. | **Fixed:** new security stamp on confirmation; the current session's cookie is re-issued (API and page), other sessions end. Test: a reset link sent to the old address before the change is refused afterwards. |
| F4 | Medium | `src/…Web/appsettings.json` (working copy) holds a real `UrlTokens:Key`. | **Not part of this change** — the owner's local, never-committed file (working rule: never commit `appsettings.json`). Keep the key in user secrets / the environment for any shared or hosted copy; rotate it if it was ever used outside this PC. |
| F5 | Low | The confirmation page did not show the address being confirmed (a forwarded link could be confirmed blindly). | **Fixed:** the signed-in account's user sees "New email: …" before the button (`PendingForAsync`; nothing is shown to anyone else). |
| F6 | Low | A recovery code could be used up by a request that then failed with "this is already your email". | **Fixed:** that check runs before re-authentication (it reveals nothing). The "not available" answer still comes after re-authentication on purpose (no probing without the password). |
| F7 | Low | Any database error on confirmation was reported as "not available"; a concurrency error (two tabs) gave a server error on the page. | **Fixed:** "not available" only when the address is now taken by another account (re-read); the page treats a concurrency error as an invalid / used link. The name/username save keeps a concurrency error as the normal 409 conflict. |
| F8 | Low | The current address heard of the change only after confirmation. | **Fixed:** a notice to the current verified address as soon as a change is asked or started (new address masked, "cancel in your profile"). Test. |
| F9 | Low/Info | The admin start can send mail to any typed address; only the per-IP auth limit applies. | **Accepted for now** (Owner / Administrator only, fixed text). Candidate: a per-tenant daily cap. |
| F10 | Info | The confirm answer differed (sign-in needed vs invalid) before the token was checked. | **Fixed:** the token is checked first; only a valid link reaches "sign in to confirm". "Not available" to Owners / Administrators on start matches the existing create-user behaviour (DT-203). |
| F11 | Info | Soft-deleted users' addresses count as taken (pre-existing store behaviour); the name/username PUT shared the sign-in rate bucket; pending address visible to `users.manage` holders; failed re-authentication audited as "SignInFailed". | PUT taken off the sign-in bucket (global limiter applies); the rest accepted as is. |

## Verified as correct
- Authorization on the server: `users.manage` on the group, then the caller's preset Owner / Administrator role in the current company (`user.ownerOrAdministratorOnly`, 403), targets limited to users of the current company and `GrantGuard` (an Administrator never edits the Owner); support sessions and custom roles with `users.manage` are refused. The client only hides buttons.
- Takeover by the new mailbox alone is blocked: confirmation needs the account's own signed-in session; the token (Identity DataProtector provider, 24 h) is bound to the user, the security stamp and the purpose `ChangeEmail:<address>:<request ticks>` — a new request or a cancel voids earlier links, a used link cannot be replayed; the link carries no address; a mail scanner opening it changes nothing (POST button).
- An Owner / Administrator cannot change their own email from Users & roles (`user.emailOwnInProfile`) — their own change always needs re-authentication.
- Re-authentication: password, and with two-step verification on a code or a recovery code, both required before anything is checked; failures count towards the throttle / lockout.
- Unique email and username (platform-wide checks, unique indexes as the final guard); row version on the name/username save.
- CSRF: antiforgery on every API write and on the account page form; rate limiting on the email-change requests and the confirmation; HTML-encoded names and addresses in the emails; every step audited with readable history (EmailChangeRequested / EmailChangeStarted / EmailChangeCancelled / EmailChanged / ProfileChangedByAdmin).

**Open after this review:** F4 (owner's local configuration) and F9 (optional cap) — no open finding in the change itself.
